# 작업 방식

## 1. 목표

[README](../README.md)의 필수 범위와 [ROADMAP](ROADMAP.md)의 체크포인트를 달성합니다. 담당 1~5가 도메인 모듈을 하나씩 맡아서 구현, 테스트, 설명까지 책임집니다. 담당별 범위는 [BACKEND_PLAN](BACKEND_PLAN.md), 모듈 구조는 [ARCHITECTURE](ARCHITECTURE.md)를 따릅니다.

기본 목표는 실제 PostgreSQL로 돌아가고 다른 컴퓨터에서도 재현되는 로컬 데모입니다. 시연은 API 문서 화면(`/docs`)으로 합니다. **UI 연결 · CI · Redis는 범위에서 뺐습니다** (2026-10-28). 외부 배포는 제출 조건에 있을 때만 추가합니다.

## 2. 역할 분담

| 작업 | 담당 | 팀원이 할 일 |
| --- | --- | --- |
| 저장소 설정, `common/database.py` · `config.py` · `main.py` 뼈대 | 지원 작업 (에이전트 활용) | 의미 있는 테스트 제공, 결과 읽기 |
| 공용 환경(Docker PostgreSQL), 실행/테스트 안내 | 지원 작업 (에이전트 활용) | 안내대로 실행, 로컬 변수 이해, API/DB 에러 읽기 |
| 보안 기반, 트랜잭션 패턴 | 지원 작업 + 관련 담당자(담당 1, 4) | 헬퍼 설명하고 쓰기, 거절/롤백 동작 테스트 |
| 도메인 모듈 4계층과 테스트 | 담당 1~5 (자기 모듈) | 정해진 범위 구현하고 결과 설명 |
| 공통 응답 형식: 목록 `Page[T]`, 에러 응답 형식(`error.code`·`message`·`details`·`request_id`) | 담당 2 | 같은 형식으로 응답하고, 자기 에러 코드를 정해 공유 |
| 슬롯 규칙 `TimeSlot`, lifespan 테이블 생성 + 시드 | 담당 3 (각자 자기 테이블 행 제공) | 자기 테이블 시드 행 설명 |
| 예약 응답 `ReservationOut` · `can_cancel` | 담당 4 | 같은 스키마로 응답 |
| 소속 확인 `is_member` | 담당 5 | 헬퍼를 써서 거절 동작 테스트 |
| 요청 로그 · 처리 시간 미들웨어, CORS | 담당 1 | 로그에 민감 정보가 없는지 확인 |
| 외부 배포 (필요한 경우) | 별도 지원 작업 | 그 환경에서 자기 API 확인 |

다른 담당 모듈의 파일을 고쳐야 하면 그 모듈 담당에게 먼저 알리고, PR 리뷰도 그 담당이 봅니다. 한 사람이 질문과 버그를 혼자 다 받지 않도록, 도움 요청은 정해진 시간에 모아서 합니다(6장).

## 3. 작업 흐름

이슈 보드는 하나만 씁니다: Backlog → Ready → In progress → Review → Integrated → Demonstrated. 담당자, 동작 하나, 입출력 예시, 실패 케이스 하나, 의존 관계, 확인 방법이 정해지면 Ready로 옮깁니다.

동작을 바꿀 땐: 계약 정하기 → 작은 실패 테스트 쓰기 → 최소한으로 구현 → 다시 실행 → 정리. 업무 규칙이면 **도메인 단위 테스트**부터 쓰고(DB 없이 빠르게 돎), 그다음 API 테스트로 연결합니다. API 문서 화면(`/docs`)에서 요청이 되는 걸 보여 줍니다.

막히면 요청 내용, 기대한 응답과 실제 응답, 로그(민감 정보 제거)를 적어서 질문합니다. 에이전트에게는 원인 설명이나 작게 시도해 볼 방법을 물어보고, 모듈 하나를 통째로 맡기지 않습니다.

## 4. 브랜치와 리뷰

main에서 짧게 쓰고 끝낼 기능 브랜치를 땁니다. 각자 따로 구현한 걸 마지막 날까지 들고 있지 않습니다.

- 브랜치 이름: `feat/<topic>`, `fix/<topic>`, `docs/<topic>`
- 커밋 메시지는 결과가 드러나게, scope는 모듈 이름으로. 예: `feat(reservation): prevent double seat restore on cancel`

PR에는 동작, 계약/스키마 변경, 실제로 돌린 테스트 결과, 알려진 한계, 재현 가능한 요청 예시를 넣습니다. 작성자가 아닌 팀원이 diff를 읽고 동작 하나를 재현해 봅니다. 공용 코드(`common/`, `main.py`)나 보안·트랜잭션 코드는 별도 기술 리뷰도 받습니다. 리뷰 후 크게 고쳤다면 다시 리뷰를 받습니다.

로컬 테스트 통과만으로 머지하지 않습니다. 관련 체크와 리뷰를 확인하고 지적 사항이 정리된 뒤 머지합니다. 테스트를 통과시키려고 테스트를 지우거나 건너뛰지 않습니다.

## 5. 변경별 확인 항목

| 변경 | 필요한 근거 |
| --- | --- |
| 단순 API | 입출력 예시, 정상·실패 테스트 |
| 업무 규칙 | 도메인 단위 테스트 (규칙 통과·위반 각 1개 이상) |
| 개인 리소스 | 실제 API로 관련 없는 사용자/운영자 거부 확인 |
| 스키마 (ORM 모델) | 빈 DB에서 앱 시작 시 테이블·시드 생성, 재시작해도 시드 중복 없음, 관련 동작 체크 |
| 예약/취소 | 실제 DB로 원자성, 좌석 1회 복구 확인 (동시 요청·재시도는 선택 과제) |
| 모듈 경계 | 도메인이 FastAPI·SQLAlchemy·Pydantic을 import하지 않음, 다른 모듈 참조가 [ARCHITECTURE 2장](ARCHITECTURE.md#모듈-사이-참조-규칙) 범위 안 |
| 공용 환경 | 작성자가 아닌 사람이 세팅/실행/테스트 안내 재현 |
| 문서 | 링크, 역할/날짜/범위가 다른 문서와 맞는지 |

실제로 돌린 명령과 결과를 PR에 남깁니다. 변경 후에는 영향받는 체크를 다시 돌립니다.

## 6. 통합과 소통

연습본 다섯 개가 아니라 공용 예제 하나만 통합합니다. D6까지 고객 예약/취소와 운영자 조회 흐름을 연결하고, 선택 과제는 그다음에 붙입니다.

마이그레이션 도구는 쓰지 않습니다. ORM 모델(테이블 구조)을 바꾸면 PR과 팀 채널에 알리고, 각자 로컬 DB를 다시 만듭니다(`docker compose down -v` → `docker compose up -d` → 앱 시작). 데이터는 시드로 다시 채워지므로 가짜 데이터만 씁니다. 모듈끼리 맞지 않으면(예: 응답 스키마, 도메인 메서드 이름) 양쪽 담당자가 같이 해결합니다.

매일 정해진 질문 시간과 짧은 통합 점검 시간을 둡니다. 각자 배운 개념 하나, 완료한 동작 하나, 막힌 것 하나, 다음 작업을 공유합니다. 회의는 짧게 합니다.

## 7. 완료 기준

- **Integrated:** 공용 통합본에서 동작하고, 관련 체크·리뷰를 통과하고, 그 모듈을 쓰는 쪽과 맞고, 작성자가 설명할 수 있음
- **Demonstrated:** 다른 팀원이 로컬 세팅을 재현하고, 필수 흐름 전체를 실제 데이터로 보여 주고, 한계도 밝힘

머지됐다고 데모가 동작한다는 뜻은 아닙니다. 최종 통합본 커밋, 실행 안내, 테스트 결과, 한계를 README에 기록합니다.

외부 배포가 필수라면 실제 URL, 배포된 통합본, 스모크 테스트 결과도 있어야 합니다.

## 8. 최종 체크리스트

- [ ] 담당 1~5 모두 자기 모듈을 4계층으로 완료하고 설명함
- [ ] 다른 팀원이 문서대로 빈 DB에서 실행·시드·테스트를 재현함
- [ ] 시드 계정으로 로그인, 식당 목록·상세, 예약 가능 조회, 예약, 내 예약 목록/상세, 취소가 실제 API로 동작함
- [ ] 운영자 조회·수정은 식당 소속을 확인하고, 고객은 다른 사람의 개인 데이터에 접근할 수 없음
- [ ] 초과 예약 없음, 중복 예약 없음, 다시 취소하면 409이고 좌석은 한 번만 복구 (동시 예약·재시도는 선택 과제)
- [ ] 각자 성공 요청 1개, 실패 1개, 테스트 1개를 설명함
- [ ] 끝낸 범위와 못 한 기능(선택 과제 포함)을 기록함
- [ ] (외부 배포가 필수일 때만) 배포 환경 체크 통과
