## D1~D3: 같이 배우기

처음 3일 동안 다섯 명 모두 각자 연습 공간에서 같은 작은 기능을 4계층으로 만듭니다. 도메인 `Restaurant` 만들기 → 메모리 리스트 레포지토리로 식당 하나 가져오기 → 서비스·라우터 연결 → ID 검증(422) → 없으면 404 → 레포지토리만 비동기 DB 조회로 바꾸기 → API 테스트. 다섯 명이 만든 예제를 전부 머지하지 않고, 하나를 골라 `src/restaurant/`에 통합해서 기준 예제로 씁니다.

저장소와 실행 환경 준비(Docker Compose PostgreSQL, `common/database.py`, `main.py` 뼈대)는 에이전트 도움을 받아 함께 처리합니다. 이 실습에서는 다음 기능에 필요한 개념만 배웁니다. 담당별로 배울 개념은 [BACKEND_PLAN.md](BACKEND_PLAN.md)를 봅니다.

## 체크포인트

- **G1:** 각자 도메인 객체 · ORM 모델 · API 스키마를 구분하고, 요청이 4계층을 지나는 순서를 설명하고, 작은 규칙 하나를 바꾸고 테스트할 수 있는가?
- **G2:** API 문서 화면(`/docs`)이나 테스트로, 여러 사람이 만든 모듈을 거치는 실제 고객 예약/취소, 운영자 조회 흐름이 동작하는가?
- **G3:** 권한, 예약 원자성, 취소 규칙이 체크를 통과하는가? (재시도·동시성 재현은 선택 과제)
- **G4:** 다른 팀원이 빈 DB에서 프로젝트를 실행하고 같은 통합본에서 체크를 재현할 수 있는가?
- **G5:** 각자 자기 모듈에서 성공 1개, 실패 1개, 테스트 1개를 설명할 수 있는가?

G1을 못 넘으면 같이 하는 실습을 더 하고 기능 범위를 줄입니다. 일정을 맞추려고 더 큰 모듈을 혼자 맡기지 않습니다.

## 역할 배정 후 첫 과제

| 담당 | 모듈 | 첫 과제 | 시작점 |
| --- | --- | --- | --- |
| 1 | `user` | 로그인, 현재 사용자 GET, 로그인 실패 테스트 | 제공되는 해시/토큰 예제 |
| 2 | `restaurant` | 404와 공개 필드를 포함한 식당 상세 → 목록 | 공통 실습 기준 예제 |
| 3 | `slot` | 슬롯 모델·`TimeSlot` 규칙 → lifespan 시드 → 날짜/인원 기준 예약 가능 조회 (꽉 찬 경우, 잘못된 입력 포함) | 시드 슬롯 |
| 4 | `reservation` (쓰기) | `Reservation` 도메인 → 예약 생성 → 취소 | 공용 인증/DB 예제, 트랜잭션 패턴 |

## 범위 줄이기

처음부터 작게 갑니다: 시드 계정/식당/슬롯, 예약 상태 2개, 운영자 목록. 식당 정보 수정은 관리 화면 없이 API 문서 화면에서 합니다.

**하지 않음**: UI 연결(Jinja2 포함), CI, Redis 캐시, Alembic 마이그레이션.

**선택 과제** (필수 흐름이 다 돌아간 뒤): 회원가입 · 로그아웃 토큰 차단(담당 1), 멱등성 · 동시성 재현 테스트(담당 4), 외부 배포(제출 조건일 때).

더 줄여야 할 때는 이 순서로 뺍니다: 식당 검색·정렬(목록·페이지만 남김) → 예약 조회 날짜 필터 → 미들웨어 처리 시간 기록. 핵심 기능과 정합성 체크는 마지막까지 남깁니다.

보안이나 예약 규칙이 체크를 통과하지 못하면, 그 흐름은 시연 범위에서 빼고 남은 결함을 공유합니다.
